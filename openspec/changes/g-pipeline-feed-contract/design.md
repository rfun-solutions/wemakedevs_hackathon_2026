## Decisions
1. **Break lives outside the PR.** The `feed-contract` job reads `vars.FEED_FIXTURE` and `vars.FEED_MODE` and passes them to the mock as env. Fixtures `sessionize-v1.json` and `sessionize-v2.json` sit on `main`. A harmless PR plus the variable flip turns CI red. Reverting the PR changes nothing; only a code fix (schema + mapper + tests) turns it green. Rejected: `chaos.json` in the PR diff (T1: Gitar reverted it).
2. **Demo = schema drift (v2).** v2 renames `startsAt/endsAt` to `starts_at/ends_at` and splits `rooms[].name` into `building/level/room`. Backup = `FEED_MODE=429`: mock returns 429 with `Retry-After: 1` for the first 2 requests, then 200. Expected fix: bounded retry honouring `Retry-After` plus last-good-feed cache.
3. **Baseline must be breakable. G creates it, A extends it.** G merges before A and ships `api/src/services/sessionize/`:
   - `schema.json`: JSON Schema for the v1 feed (`sessions[]` with `startsAt`/`endsAt`/`roomId`/`categoryItems`, `rooms[]`, `categories[]`).
   - `fetchFeed.ts`: `export async function fetchFeed(url: string, opts?: { timeoutMs?: number; fetchImpl?: typeof fetch }): Promise<unknown>`. Timeout defaults to 10 s. It throws `FeedHttpError` (with `status`) on non-2xx and has **no retry**.
   - `mapper.ts`: `export function mapFeed(feed: unknown): MappedSession[]`. It validates against `schema.json` with Ajv and throws `FeedShapeError` on mismatch. `MappedSession = { id, title, description, startsAtLocal, endsAtLocal, venueTz: 'America/Denver', roomRaw, track, audienceLevel, categories: string[] }`, with naive local time strings and no speaker fields.
   - Exports `FeedHttpError` (from `fetchFeed.ts`) and `FeedShapeError` and `MappedSession` (from `mapper.ts`).
   A never edits G's files. It wraps `mapFeed` in its own `api/src/services/schedule/derive.ts`, which adds the derived fields (building, level and room via `schedule/rooms.ts`, UTC instants via `schedule/time.ts`, access tags), and calls `fetchFeed` and `derive.ts` from `schedule/ingest.ts`. That keeps the Gitar on-stage feed fix in `mapper.ts` free of A's code and avoids a wave-1 overlap. A adds no retry and no v2 handling, because those are the demo fixes. A also creates no second schema, mapper, fetcher or v1 fixture. G's file headers document this handoff. The v1 fixture `feed-contract/fixtures/sessionize-v1.json` holds 60 sessions and is shared with A's tests.
4. **Job layout.** `feed-contract` starts `feed-contract/mock-upstream` (small Node http server, no deps) as a background step or service container built from the same folder; step 1 validates the served feed against the schema (Ajv), step 2 runs the mapper and fetch tests with Vitest (C0's runner: `npx vitest run api/src/services/sessionize`). The tests assert against the live mock (variable-driven) and against committed fixtures (v1 always; v2 tests are what Gitar adds).
5. **Dash0 CI traces.** `ci-traces.yml` triggers on `workflow_run` (workflows `lint-unit`, `e2e-mobile`, `a11y`, `build-image`, `feed-contract`, `deploy`; type `completed`) and exports only runs triggered by `merge_group` or a push to `main`, because each exported run is another job and CI capacity is the build-day ceiling (adding PR runs needs the orchestrator's OK), job permissions `actions: read` and `contents: read`, token from Secret `DASH0_INGEST_TOKEN` (ingest-only). Author emails: the action sends commit author emails unredacted. Mitigation: repo contributors use GitHub noreply addresses (set `user.email` in `AGENTS.md` working agreement; deploy bot already uses noreply), and a task checks the first trace in Dash0 and records the finding. If real emails appear, disable the workflow before submission rather than ship them. The action cannot redact itself (UNVERIFIED: check for an input at apply time).
6. **Release and deploy bot.** C0's `deploy.yaml` (workflow `deploy`), owned by G after C0 merges, runs on `push` to `main`: skip if head commit message starts `deploy:`. Job `image` (packages: write) builds and pushes `ghcr.io/<repo>:<sha>` using docker actions at versions pinned in the vault. Job `deploy` mints a token with `actions/create-github-app-token@v3.3.0` (`DEPLOY_BOT_APP_ID` variable, `DEPLOY_BOT_PRIVATE_KEY` secret), replaces only the `newTag:` line of the pre-created `images:` block in `deploy/kustomization.yaml` (single-line `sed` or `yq -i`; not `kustomize edit set image`, which may reorder the file and drop the per-change marker comments; whether it preserves them is unverified), commits `deploy: <sha>` as `<slug>[bot]`, and pushes to protected `main`. `concurrency: {group: deploy-main, cancel-in-progress: false}` plus `git pull --rebase` before push (T6b race). The repo `rfun-solutions/wemakedevs_hackathon_2026` is a public organisation repo, where the ruleset and App bypass were verified (T6, T6b).
7. **Gitar interplay.** `.github/workflows/*` is never edited by Gitar, so all fixes land in `api/` and tests. Runbook relies on `.gitar/review/external-calls.md` (C0) and adds nothing to it.

8. **G4 rules from production.** Workflow `.github/workflows/rules-from-prod.yml` (`schedule: '7 * * * *'` plus `workflow_dispatch` with inputs `window` (default `1h`) and `force` (default `false`); top-level `permissions: contents: read`; `concurrency: {group: rules-from-prod, cancel-in-progress: false}`, deliberately NOT the `deploy-main` group, because a new pending run in a group cancels the older pending one and could drop a deploy). It runs `node scripts/rules-from-prod.mjs`, which has two parts:
   - `queryPromQL(expr)`: `POST https://api.us-west-2.aws.dash0.com/api/prometheus/api/v1/query` with `Authorization: Bearer $DASH0_TOKEN`, form body `query=<expr>`, 10 s timeout. The path is verified by live test T9 and the route label is `dash0_operation_name` (T9 addendum); they sit in one `CONFIG` object at the top of the script.
   - `renderHotPaths(result, now)`: a pure function that returns the file text.

   **Shared query contract** (F's server poller uses the same two expressions; keep them identical):
   - Routes (verified in T9 addendum): `histogram_quantile(0.95, sum by (le, dash0_operation_name) (rate(dash0_spans_duration_seconds_bucket{service_name="kubecompanion", dash0_operation_name=~"(GET|POST|PUT|PATCH|DELETE) /.+"}[<window>])))`; the route is the label `dash0_operation_name` with the method prefix stripped. Fallback if no operation names carry route templates: `histogram_quantile(0.95, sum by (le, route) (rate(kc_app_http_server_duration_bucket[<window>])))` (C0 emits it).
   - Captions: `histogram_quantile(0.95, sum by (le, engine) (rate(kc_captions_segment_ms_bucket[<window>])))` (E records the histogram server-side).

   **Hot route** = p95 over 300 ms, excluding `/healthz`, `/readyz`, `/api/ping` and `/api/status*`; at most 5, slowest first. **Caption breach** = any engine's p95 over 4000 ms.

   File format of `.gitar/review/hot-paths.md`:
   ```
   <!-- Generated by rules-from-prod. Do not edit by hand; the next run overwrites it. -->
   # Hot paths (written by production telemetry)
   Generated from Dash0 at 15:52 America/Denver (2026-11-09T22:52:00Z), window 15m, region us-west-2.
   Measured p95: /api/agenda 2.1 s; /api/sessions 240 ms. Caption lag p95: whisper 3.2 s, webspeech 1.1 s.

   ## Rules
   - HP-1: Changes to the handler for `/api/agenda` must keep p95 under 300 ms and must keep database queries out of loops (one query or one batched query per request); production p95 is 2.1 s as of 15:52 (Dash0, 15m window).
   - CAP-1 (Promise P1): Changes under `web/src/lib/speech/` must keep caption lag p95 under 4 s and the chunk length at or under 5 s; production caption lag p95 is 3.2 s on whisper and 1.1 s on webspeech as of 15:52, within the limit.
   ```
   **Numbers go inside each rule sentence.** T10 (2026-11-09) showed Gitar's inline findings open with `Per the review rule "..."` and quote the rule sentence, never the header. So every rule sentence contains the route or folder, the limit, the live Dash0 p95 and the HH:MM it was measured; the header is for humans only. With no hot routes the Rules list says "No route is over 300 ms as of HH:MM" and keeps CAP-1. CAP-1 is always written, so the file shape is stable; it ends "over the limit" when breached. Promise ids (owned by D, `ACCESS-PROMISES.md`) go into the sentence, not the header: CAP-1 always reads `CAP-1 (Promise P1)`, and an HP rule for `/api/notes` reads `HP-n (Promise P2)`; other routes carry no promise id. `CONFIG.promiseByRoute = { '/api/notes': 'P2' }`. Times use `Intl` with `America/Denver` explicitly (`time-zones.md`).

   **Commit rule.** The workflow commits only when the set of hot routes or the caption-breach state changed, or when `force` is true, so hourly runs do not churn `main`. The deploy-bot App token (`actions/create-github-app-token@v3.3.0`) commits `rules: update hot-paths from Dash0 (HH:MM)` with the bot noreply identity, runs `git pull --rebase` and retries the push once. Only `.gitar/review/hot-paths.md` is ever staged; the script refuses to write any other path. `deploy.yaml` skips head commits starting with `rules:` as well as `deploy:`, because no image is needed. T10 verified the path end to end: the bot push landed on protected `main` in 8 s and a PR opened 82 s later got rule-quoting findings about 60 s after opening. Gitar's footer still says "No rules evaluated" (that refers to `.gitar/rules`, not `.gitar/review`).
9. **G5 runbook: the on-stage Gitar fix (DECIDED by the user 2026-11-08).** D prepares branch `bugfix/KC-<n>-card-contrast` (one token in `tokens.css` drops the show-to-person card text to 3.9:1). 10. **G3 budget break: prepared repo-evidence PR (DECIDED by the user 2026-11-08).** T8 PASSED on 2026-11-09 (review in 34 s, fix commit in 51 s lowering a new component's memory request from 1Gi to 512Mi, CI green at about 68 s, script and rule untouched). No app spans. CI traces via otel-cicd-action show job and step durations; the runbook screenshot is the trace of the red then green `feed-contract`.

## Risks
- G4 needs real traffic: before the 15:45 slowdown the query may return no hot routes. The runbook dispatches the workflow with `window=15m` right after the load, and keeps the dress-rehearsal PR as a fallback tab.
- A bot writing to `main` can alarm judges: it writes one file under `.gitar/review/`, as the bot identity, with the numbers in the header.
- Gitar may take longer or treat CI-only failures differently: runbook has a manual nudge comment and a pre-recorded run.
- Variable left at `v2` breaks every PR: runbook ends with a reset step and a guard check.

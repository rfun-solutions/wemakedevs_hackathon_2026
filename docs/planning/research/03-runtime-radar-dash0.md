# Runtime research: Radar, Dash0, where to run (information only, no decisions)

Compiled 2026-11-08. Sources: cloned github.com/skyhook-io/cnh-starter (README.md, AGENTS.md, Dockerfile, deploy/, scripts/local-cluster.sh, deploy.yaml), join.cnh.radarhq.io (curl), Dash0 and Radar docs. Items marked (unverified) come from my memory or inference, not a fetched page.

## 1. Radar

**What it is.** Open-source (Apache-2.0) Kubernetes UI from Skyhook, single Go binary, with a built-in MCP server. Shows issues, topology, timeline/changes, Helm, GitOps (Argo CD/Flux), traffic, 44-check cluster audit. https://github.com/skyhook-io/radar
- OSS: runs locally via kubeconfig (`curl -fsSL https://get.radarhq.io | sh && kubectl radar`, `brew install kubectl-radar`), or in-cluster via Helm (`helm repo add skyhook https://skyhook-io.github.io/helm-charts; helm install radar skyhook/radar -n radar --create-namespace`). Local MCP: `http://localhost:9280/mcp` (read-only `/mcp-readonly`). OSS AI investigations run through a local agent CLI (Claude Code etc.), need auth off, and do not run on in-cluster installs.
- Radar Cloud (app.radarhq.io): hosted, multi-cluster, alerts, hosted AI investigations. A cluster connects by running a Helm command from "Connect a cluster" (carries a cluster token, so paste in terminal only). Own org is free: up to 3 clusters, 100 AI investigations/month (cnh-starter README).
- Hosted MCP: `claude mcp add --scope user radar-cloud --transport http https://api.radarhq.io/mcp`, then `/mcp` > Authenticate. Pick **Cloud Native Hackathon** under "Organization access" for the event cluster. Every tool takes a `cluster` id (about 40 clusters in the org).

**MCP tools** (https://radarhq.io/docs/features/mcp, page only partly read): issues, diagnose (evidence bundle), get_dashboard, top_resources, list_resources, search, get_resource, get_topology, get_neighborhood, get_events, get_changes, get_pod_logs, get_workload_logs, list_helm_releases, get_helm_release, list_packages, get_cost, get_rightsizing, query_prometheus, discover_metrics, get_prometheus_rules, get_cluster_audit, get_cluster_upgrade_readiness, manage_node, wait_for, exec_pod (opt-in). Starter docs also name write tools: apply_resource, manage_workload (restart), manage_cronjob, manage_gitops (Argo sync).

**AI investigation.** Read-only MCP tools; ends in a structured verdict with evidence cards, ruled-out hypotheses and typed remediation steps. Can start from a resource ("Investigate" button) or a free-text question. Applying a fix runs in a separate write-enabled session with a verification turn. Investigations start private; mark **Shared** for others to read. Judges want at least one; an all-clear after a release also counts (starter README).

**cnh-starter findings (the key facts)**
- Each team gets its OWN virtual cluster (vcluster), cluster-admin, via **join.cnh.radarhq.io** (form page "Get your team cluster"; join code given at kickoff; 3-4 min; progress at `join.cnh.radarhq.io/status/<team-name>`). Not shared namespaces. Radar Cloud org "Cloud Native Hackathon" lists ~40 team clusters plus platform cluster `cnh`; you only access yours. Clusters/org access end Fri Nov 13.
- Provisioned: starter app in ns `team-<team>` at **public URL `https://<team>.cnh.radarhq.io`** (platform routes to Service `app` port 80 in that namespace; no other hostnames, no LoadBalancer/NodePort). Pre-installed: Argo CD (ns argocd, no UI; Applications in `team-*` ns, project `team-<team>`), Argo Rollouts, Gateway API CRDs, metrics-server, Prometheus (ns monitoring, 30s scrape, 7d retention, scrapes pods annotated `prometheus.io/scrape: "true"`; no node-exporter, no Alertmanager), CloudNativePG operator (ns cnpg-system), Radar (ns radar, do not upgrade).
- **Budget (one total across all namespaces, incl. anything installed): 2 CPU / 4 GiB requests, 4 CPU / 8 GiB limits, 4 PVCs / 20 GiB (gp3).** Containers without requests/limits get 100m/128Mi req, 500m/512Mi limit. Over budget = pod Pending with `SyncError ... exceeded quota: team-quota`. Starter Deployment: 2 replicas, 100m/128Mi req, 500m/256Mi limit.
- **Host refuses privileged, hostPath, hostNetwork, hostPID pods** (stay Pending, SyncError event). Node-agent charts (log collectors, node exporters) often need these.
- Workflow: template repo -> `./scripts/setup.sh <team>` -> GitHub Action builds image to GHCR (must be public; repo must be public) and commits `deploy:` sha to deploy/kustomization.yaml -> Argo CD syncs from main (applied via Radar MCP). Repo has `.agents/skills/` (get-started, ship, debug-failure, canary-release, demo-story) and AGENTS.md that steer the agent. Starter app is Node 22 (port 8080, /healthz, /readyz); can be replaced by any language if Dockerfile changed.
- Secrets: create via Radar Cloud UI or kubectl in ns, reference via secretKeyRef; never in repo/image.
- kubectl: kubeconfig in Secret `default/kubeconfig`, key `config` (copy via Radar UI); server `https://<team>.vc.cnh.radarhq.io`; token valid 24h.
- Examples shipped: postgres (CNPG, `db-rw:5432`), canary (Argo Rollouts), hpa, agent-workflows.
- Schedule from README: 11:00 get cluster + connect agent before writing code; screenshot Checks as "before" in first hour; 17:30 tell the story from Radar (timeline, investigation, Checks before/after). Note: submissions close 17:30 in the starter's sample schedule.
- Known noise every team sees (don't investigate): CoreDNS rewrite issue, startup warnings, `app-code` ConfigMap missing on first sync, applicationset-controller scaled to 0, "Can upgrade Radar".
- Bring-your-own cluster is explicitly allowed and "still counts for judging": use your own Radar Cloud org (not the hackathon one), name cluster exactly `<team>`, delete `httproute.yaml` from kustomization, use `argocd/application-byo.yaml`. You lose public URL, Prometheus, organizer access. `scripts/local-cluster.sh <team>` builds a k3d/kind/minikube cluster mirroring the event one (k3s v1.33.6, Argo CD 10.11.7, Rollouts, Gateway CRDs), needs ~4 GB RAM free; `--pull` pre-downloads ~500 MB (do this on good Wi-Fi). Radar Cloud outage fallback: local Radar with kubeconfig.
- After event: hackathon participants get 3 months Radar Enterprise free (tell them org name by Nov 30).
- Rule 1 caveat: coding must start after kickoff. Cloning/reading starter is allowed.

## 2. Dash0

- **Trial:** 14-day unlimited free trial, no card, all features incl. Agent0 credits; no permanent free tier listed. Pricing after: per million spans/logs/web events $0.06 ingest + $0.54 storage; metrics $0.02/M; Agent0 $0.60/credit. https://www.dash0.com/pricing (trial has no stated caps).
- **Regions for MCP/ingest:** eu-west-1, eu-central-1 (AWS), europe-west4 (GCP), us-east-1, us-west-2 (AWS). Pick US region for latency; endpoint under Settings > Endpoints.
- **Dash0 MCP:** `claude mcp add --transport http --scope user dash0 https://api.<region>.<cloud>.dash0.com/mcp` (e.g. api.us-east-1.aws.dash0.com), then `/mcp` > dash0 > sign in (OAuth, 15 min tokens auto-refresh). Or header `Authorization: Bearer <token>` (needs read access). Tools: read-only (service catalog, PromQL/SQL, log+span search, trace lookup, failed check rules, synthetic checks, SLOs, dashboards, websites), `listDatasets`, and Agent0 delegation `runTask` / `waitForTask` (consumes credits; admin can disable). https://www.dash0.com/docs/dash0/ai/mcp
- **Agent0:** investigates telemetry, reads connected GitHub/GitLab code, proposes dashboards, check rules, code fixes and pull requests; sandbox can clone repos; chat at app.dash0.com/agent0, "Live Insights" per service, Slack `@dash0`. https://www.dash0.com/docs/dash0/ai/agent0
- **Operator (helm):** `helm repo add dash0-operator https://dash0hq.github.io/dash0-operator && helm install --wait -n dash0-system --create-namespace --set operator.dash0Export.enabled=true --set operator.dash0Export.endpoint=<OTLP gRPC> --set operator.dash0Export.apiEndpoint=<API> --set operator.dash0Export.token=<token> dash0-operator dash0-operator/dash0-operator`. Then enable monitoring per namespace. Auto-instruments Java, Node.js 16+, .NET, Python (opt-in), Ruby (opt-in); Go not listed (needs manual SDK or eBPF). Needs k8s >=1.25.16. https://www.dash0.com/docs/dash0/monitoring/kubernetes/dash0-operator/overview
- **Operator footprint/risk on the event cluster:** default requests = manager 50m CPU/128Mi, DaemonSet collector 500Mi, cluster-metrics collector 500Mi, config reloaders, agent0-connector 64Mi -> roughly 1.3-1.5 GiB requests of the 4 GiB budget, before the app. Collector DaemonSet uses **host ports 40317/40318** and mounts host log dirs (`/var/log/pods`, hostPath) for filelog; the docs describe hostPath for filelog offsets and OpenShift SCC for "host log directories via hostPath". The event host **refuses hostPath/hostNetwork-style pods**, so the operator's collector DaemonSet very likely stays Pending (inference, untested; docs I fetched do not say whether log collection can be turned off). Also the operator's webhooks/CRDs should be fine for cluster-admin in a vcluster. Operator also supports GKE Autopilot via `operator.gke.autopilot.enabled` (some features off). https://www.dash0.com/docs/dash0/monitoring/kubernetes/dash0-operator/advanced-configuration , .../platform-specific
- **Lower-risk alternatives on a restricted cluster (unverified specifics):** (1) app SDKs export OTLP directly to Dash0 (env `OTEL_EXPORTER_OTLP_ENDPOINT`, `Authorization: Bearer <token>`, optional `Dash0-Dataset` header; exact values prefilled at app.dash0.com/onboarding); (2) one small in-cluster OTel Collector Deployment (no hostPath) forwarding to Dash0; token in a Secret. Pod logs then come via OTel logs SDK/log bridge rather than filelog.
- **SDKs:** Node: `@opentelemetry/sdk-node` + auto-instrumentations (or Dash0 operator injection); Python: `opentelemetry-distro` + `opentelemetry-instrument`; Go: manual SDK (no operator injection listed). Dash0 has agent skills for instrumentation (tessl registry dash0/agent-skills: otel-instrumentation, otel-collector) which could guide Claude. Per-language Dash0 pages not fetched (hub: https://dash0.com/hub/integrations).
- **Browser RUM:** `npm install @dash0/sdk-web`; `init({ serviceName, endpoint: { url, authToken } })` early in page load. Captures page views, nav timing/web vitals, fetch/XHR, errors, optional rrweb session replay (separate bundle). Token needs Ingesting permission on dataset; **client tokens are public by design** (use per-site token, inject at build). Same-origin requests propagate trace headers to backend automatically; cross-origin needs propagator config. `sessionSamplingRate` available. https://www.dash0.com/docs/dash0/miscellaneous/tooling/web-sdk/overview (npm package name appeared as both `@dash0/sdk-web` and `@dash0hq/sdk-web` in search results: verify).
- **Dashboards as code:** Perses format. Via operator (`PersesDashboard` CRD, perses.dev v1alpha1/v1alpha2), Terraform provider, or `dash0` CLI (accepts PersesDashboard files); validate with `percli`. GitOps caveat: ignore `spec.conversion` on the persesdashboards CRD. https://www.dash0.com/docs/dash0/dashboards/manage-dashboards-as-code
- **Check rules (alerts):** operator syncs `PrometheusRule` resources. **Synthetic checks:** `Dash0SyntheticCheck` CRD (operator) or `dash0 synthetic-checks` CLI; in-cluster private-location worker exists (not available on Autopilot). https://www.dash0.com/docs/dash0/monitoring/synthetics/manage-synthetic-checks-as-code
- **SLOs:** docs say **Private Beta, enabled per organization by the Dash0 team, creation API-only** (no self-serve UI, no operator CRD found). Likely needs asking Dash0 staff at kickoff to enable. https://www.dash0.com/docs/dash0/monitoring/alerting/slos
- **Can it run alongside Radar on the event cluster?** App-level yes (SDK/collector egress to Dash0 is just outbound HTTPS; Prometheus annotations unaffected). Operator: uncertain/likely blocked (above). Both can also run on a BYO cluster.

Other considerations:
- Wi-Fi: event cluster only needs laptop->Radar Cloud/GitHub/Dash0 over HTTPS; app URL is served from the cloud so phones can use cellular. Pre-pull images (`local-cluster.sh --pull`) if any local fallback is wanted. Radar OSS local is the documented fallback if Radar Cloud is down.
- Elasticsearch: not provisioned on event cluster; with the 4 GiB request / 4 PVC budget, a single-node ES is tight alongside app, Postgres and any collector. Options: Elastic Cloud trial (outside cluster), start-local on laptop (not reachable from event cluster), or ES on a BYO cluster. Only matters if the Elastic track is pursued.
- Gitar: GitHub App on the repo; independent of runtime, but the starter's Action commits `deploy:` SHAs to main (`[skip ci]`), so branch protections or Gitar auto-apply commits need `git pull --rebase` handling.
- Language: starter Dockerfile is Node-only; other languages require Dockerfile edits and Action still builds via same workflow.

## 4. "Real issue" scenarios (Agent0 / Radar friendly)

Note starter says: don't break things on purpose for the demo ("Nothing broke? Investigate your app after a release; an all-clear counts") whereas the Dash0 track wants Agent0/MCP to find and fix "a real issue live". Hackathon guidance on organically occurring issues is thus preferred; below are scenario types, not a decision.

- **OOMKill:** app limit 256Mi in starter; an unbounded in-memory cache/leaky array (e.g., unbounded session or search index) leads to OOMKilled, CrashLoopBackOff. Radar issues/diagnose show last state + events + memory chart (Prometheus); Dash0 shows process/memory metrics + restarts.
- **Bad config / bad rollout:** wrong env var/secret key ref (CreateContainerConfigError), failing readiness probe, bad image tag (ImagePullBackOff, e.g. private GHCR image), over-quota Pending (`exceeded quota: team-quota`). Radar timeline + get_changes pinpoint the commit/diff; fits "AI investigation after a release".
- **Latency / N+1 / slow query:** unindexed DB query or N+1 calls in schedule search; visible as slow spans in Dash0 traces + RUM web vitals, Agent0 can read code on GitHub and propose a PR. Introduced via a code path or env flag.
- **Failing dependency:** Postgres down/CNPG failover, external API (sessions feed, maps) timing out; shows as error spans, retries, readiness flapping; Radar topology/neighborhood shows dependency.
- **Frontend error:** unhandled JS error or failed fetch on a specific browser route, visible only via RUM, traced to backend span through trace propagation.
- **Chaos tooling:** simplest = a feature-flag/env var or hidden `/chaos` endpoint in the app (latency, error rate, memory leak) toggled via git or ConfigMap. Chaos Mesh / Litmus / Chaos Mesh daemons need privileged/hostPath/hostNetwork components, so they are unlikely to run on the event cluster (inference; check chart values); fine on local kind/k3d. Argo Rollouts canary with a bad version (examples/canary) is a built-in, host-permitted way to produce a real failed release with analysis.
